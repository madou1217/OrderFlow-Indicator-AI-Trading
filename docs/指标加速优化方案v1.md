# 指标加速优化方案 v1

## 1. 目标

本方案只解决 `orderflow-indicator-engine` 在 `startup replay / overlap repair / live repair` 阶段 `compute_ms` 过高的问题。

本方案有三个硬约束，不得破坏：

- 必须继续严格按照 [指标.md](/data/docs/指标.md) 产出指标
- 必须保证指标计算结果准确
- 必须保证指标计算过程稳定，不引入“偶尔更快但结果漂移”的优化

因此，本方案只允许做“严格等价实现优化”，不允许做以下妥协：

- 不允许减少指标数量
- 不允许减少窗口数量
- 不允许缩短 lookback
- 不允许跳过事件、level 或 heatmap 相关产物
- 不允许为了速度放松完整性门槛

## 2. 当前主因判断

当前 `ReplayMaterialize` 阶段单分钟日志里，`compute_ms` 通常显著高于：

- `snapshot_write_ms`
- `level_write_ms`
- `event_write_ms`
- `feature_write_ms`
- `progress_commit_ms`

这说明瓶颈主要在“每分钟指标计算与结果构造”本身，而不是最终写库。

从代码复核看，主要热点集中在：

- `IndicatorContext` 的大对象 clone
- `absorption / initiation / exhaustion` 三类事件检测的重复全历史扫描
- `i05_orderbook_depth` 对 heatmap 的重遍历和大量 row 构造
- 多个事件检测函数里反复构造相同历史序列 `Vec<f64>`

## 3. 优化方向

### 3.1 消掉 `IndicatorContext` 的三次大拷贝

当前路径：

- [context.rs](/data/systems/indicator_engine/src/indicators/context.rs#L163) 的 `IndicatorContext::from_bundle(...)` 已经先把整段 `WindowBundle` 历史数据 clone 进 `IndicatorContext`
- [dispatcher.rs](/data/systems/indicator_engine/src/runtime/dispatcher.rs#L113) 到 [dispatcher.rs](/data/systems/indicator_engine/src/runtime/dispatcher.rs#L115) 又把整个 `ctx` clone 给 `flow / deriv / orderbook` 三组 worker

这意味着每个分钟至少会重复复制：

- `history_futures`
- `history_spot`
- `trade_history_futures`
- `trade_history_spot`
- `funding_changes_* / funding_points_* / mark_points_*`
- 当前分钟 `MinuteWindowData` 里的 `profile / force_liq / heatmap`

优化方式：

- 把 `IndicatorContext` 改成 `Arc<IndicatorContext>` 或拆成共享只读结构
- worker 间只共享不可变上下文，不再对整份上下文做三次深拷贝

准确性与稳定性边界：

- 不改任何指标公式
- 不改任何窗口和 lookback
- 只改内存所有权与共享方式
- 只要上下文保持只读，这一改动对结果应严格等价

优先级：最高

### 3.2 把同一套 all-history 事件检测改成共享结果

当前存在明显重复计算：

#### absorption

- [i06_absorption.rs](/data/systems/indicator_engine/src/indicators/i06_absorption.rs#L453)
- [i08_bullish_absorption.rs](/data/systems/indicator_engine/src/indicators/i08_bullish_absorption.rs#L19)
- [i10_bearish_absorption.rs](/data/systems/indicator_engine/src/indicators/i10_bearish_absorption.rs#L19)

同一套 `detect_absorption_all_history(ctx)` 被计算了 3 次。

#### initiation

- [i07_initiation.rs](/data/systems/indicator_engine/src/indicators/i07_initiation.rs#L423)
- [i09_bullish_initiation.rs](/data/systems/indicator_engine/src/indicators/i09_bullish_initiation.rs#L19)
- [i11_bearish_initiation.rs](/data/systems/indicator_engine/src/indicators/i11_bearish_initiation.rs#L19)

同一套 `detect_initiation_all_history(ctx)` 被计算了 3 次。

#### exhaustion

- [i12_buying_exhaustion.rs](/data/systems/indicator_engine/src/indicators/i12_buying_exhaustion.rs#L506)
- [i13_selling_exhaustion.rs](/data/systems/indicator_engine/src/indicators/i13_selling_exhaustion.rs#L16)

同一套 `detect_exhaustion_all_history(ctx)` 被计算了 2 次。

优化方式：

- 引入事件族级别的共享预计算结果
- 每分钟只计算一次：
  - absorption all-history events
  - initiation all-history events
  - exhaustion all-history events
- `bullish / bearish / base` 指标只做过滤、投影和封装，不再重复扫描全历史

准确性与稳定性边界：

- 必须继续复用同一套检测函数
- 不改事件定义、阈值、方向判定、窗口覆盖逻辑
- 只是把“一次算多处用”替代“多次重复算”

优先级：最高

### 3.3 把 `i05_orderbook_depth` 的 heatmap 派生结果做成单次预计算

当前 [i05_orderbook_depth.rs](/data/systems/indicator_engine/src/indicators/i05_orderbook_depth.rs#L56) 到 [i05_orderbook_depth.rs](/data/systems/indicator_engine/src/indicators/i05_orderbook_depth.rs#L136) 会在每次执行时：

- 遍历 futures heatmap
- 选 `audit ticks`
- 生成 `level_rows`
- 生成 `levels`
- 生成 `heatmap_summary_fut`

这和慢日志里的高 `level_count` 直接对应。

优化方式：

- 在进入指标计算前，针对当前分钟 futures heatmap 做一次预计算
- 产出共享的中间结果，例如：
  - `heatmap_summary_fut`
  - `selected_audit_ticks`
  - `level_rows`
  - `levels`
  - `peak_bid_tick / peak_ask_tick / peak_total_tick / peak_abs_net_tick`
- `i05_orderbook_depth` 直接消费这份预计算结果，不再在指标内部重复遍历和构造

准确性与稳定性边界：

- 必须仍然使用真实 heatmap
- 必须保持 `level_rows / levels / summary` 的计算逻辑完全一致
- 不能做“降级 heatmap”或“减少 level 数量”的妥协

优先级：高

### 3.4 把事件检测里反复构造的历史序列改成共享预处理

当前这些函数都会先从整段历史映射出多个 `Vec<f64>`：

- [i06_absorption.rs](/data/systems/indicator_engine/src/indicators/i06_absorption.rs#L60)
- [i07_initiation.rs](/data/systems/indicator_engine/src/indicators/i07_initiation.rs#L56)
- [i12_buying_exhaustion.rs](/data/systems/indicator_engine/src/indicators/i12_buying_exhaustion.rs#L61)

常见重复构造包括：

- `high`
- `low`
- `close`
- `delta`
- `relative_delta`
- `spot_rdelta`
- `spot_cvd`

优化方式：

- 为当前分钟构建一次共享 `HistoryViews / PrecomputedSeries`
- 事件检测函数直接读取共享切片或共享向量
- 避免每个检测函数都重新遍历 `history_futures/history_spot` 再构造一次相同序列

准确性与稳定性边界：

- 历史序列的值和顺序必须与当前逻辑完全一致
- 不允许做采样、截断或精度降级
- 只允许做“同值缓存”

优先级：高

## 4. 推荐实施顺序

1. 消掉 `IndicatorContext` 三次大拷贝
2. 事件族级别共享 `all-history` 检测结果
3. 共享历史序列预处理
4. `i05_orderbook_depth` heatmap 派生结果单次预计算

说明：

- 第 1、2 步最可能直接显著降低 `compute_ms`
- 第 3 步会进一步降低事件类指标的重复内存分配和遍历成本
- 第 4 步对 `orderbook_depth` 有针对性收益，但要严格守住 heatmap 产物一致性

## 5. 验收标准

完成后至少需要验证：

- 同一 `ts_bucket` 下，新旧实现的 `feat.indicator_snapshot` 逐指标 payload 一致
- 同一 `ts_bucket` 下，新旧实现的 `evt.*` 事件条目一致
- 同一 `ts_bucket` 下，新旧实现的 `feat.indicator_level_value` 和 `feat.liquidation_density_level` 一致
- `ReplayMaterialize` 阶段 `compute_ms` 明显下降
- 不引入新的缺指标、缺事件、缺 level 情况

## 6. 总结

本方案不是改公式，而是把当前明显重复的 clone、历史扫描、heatmap 派生和序列构造改成共享只读与共享预计算。

只要实现时严格遵守“同值、同序、同阈值、同窗口”的约束，这些优化可以在不改变 [指标.md](/data/docs/指标.md) 语义的前提下，显著降低 `compute_ms`。
