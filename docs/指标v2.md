> 本文只讨论以下范围：
> - `orderflow-market-data-ingestor`

> - `orderflow-indicator-engine`
> - 最终写入 `/data/systems/llm/temp_indicator/*.json` 的指标结构

## 1. 目标与边界

本次新增两类真正来自外部新数据源的指标：

- `i25 open_interest`
- `i26 long_short_ratios`

目标不是让模型去猜几分钟后的涨跌，而是给上层完整提供“仓位结构”这一层信息，补齐当前系统只看价格、成交、订单流、盘口、funding、liquidation，但**看不到总持仓和多空拥挤**的问题。

本次设计的硬要求：

- 最终 `temp_indicator` 中必须出现：
  - `indicators.open_interest`
  - `indicators.long_short_ratios`
- 两个指标都必须能稳定提供这 5 个窗口：
  - `5m`
  - `15m`
  - `4h`
  - `1d`
  - `3d`
- 改造边界只限于：
  - `orderflow-market-data-ingestor`
  - PostgreSQL 表结构与写入链路
  - `orderflow-indicator-engine`

## 2. 当前系统缺的是什么

当前已有指标已经能看到：

- trade / footprint / cvd / whale
- orderbook_depth / bbo / ofi / obi
- funding / mark / index / premium
- liquidation / PVS / TPO / RVWAP / FVG / EMA / VPIN

但当前系统仍然看不到两类关键信息：

- **总持仓是否在继续堆积或卸掉**
  - 这对应 `Open Interest`
- **市场和 Top Trader 的拥挤方向**
  - 这对应 `Global/Top Long-Short Ratios`

所以这次的核心不是再加一个“更聪明的订单流指标”，而是补上衍生品盘面里最缺的一层：**仓位结构**。

## 3. 外部数据源设计

## 3.1 Binance 数据源

### Open Interest

- 当前 OI：
  - `GET /fapi/v1/openInterest`
- OI history：
  - `GET /futures/data/openInterestHist`

### Long-Short Ratios

- Global Long/Short Account Ratio：
  - `GET /futures/data/globalLongShortAccountRatio`
- Top Trader Long/Short Account Ratio：
  - `GET /futures/data/topLongShortAccountRatio`
- Top Trader Long/Short Position Ratio：
  - `GET /futures/data/topLongShortPositionRatio`

## 3.2 接入方式

这几类源在 Binance 当前公开文档中都是 **REST**，不是公开 market-data WS stream。

因此设计上应采用：

- `current OI`：每 `1m` 轮询一次
- `OI history / ratios`：统一按 `5m` 为规范时钟轮询

## 3.3 为什么规范时钟用 5m

因为这次的硬目标窗口是：

- `5m`
- `15m`
- `4h`
- `1d`
- `3d`

全部都可以由 `5m` 序列稳定滚动聚合：

- `5m = 1`
- `15m = 3`
- `4h = 48`
- `1d = 288`
- `3d = 864`

所以本次方案不使用多套原始 period 并行接入，而是统一：

- OI history：只拉 `period=5m`
- ratios：只拉 `period=5m`

这样数据库、回放、重算、窗口一致性都会简单很多。

## 3.4 REST 限流与发布时间滞后策略

这部分在开工前必须先定死，不然实现时很容易出现两类问题：

- 遇到 `429` 直接丢请求，导致 OI / ratio 缺桶
- 在 `5m` 边界立刻请求，结果不同 endpoint 返回的不是同一根最新闭合桶

### 429 / 5xx 回退策略

本次设计要求所有 OI / ratio REST 请求统一走重试包装器：

- 对 `429`、`418`、`5xx` 进行重试
- 如果响应头里有 `Retry-After`，优先遵守
- 否则使用指数回退 + 抖动：
  - `3s`
  - `6s`
  - `12s`
  - `24s`
  - `48s`
  - 后续封顶 `60s`
- 总重试时长上限：
  - `5m`

超过 `5m` 仍未成功时：

- 记录失败指标
- 记录 ops/backfill 缺口
- 本轮结束，等待下一次调度继续补齐

### 5m bucket 发布时间实测

我在 `2026-03-26 UTC` 对 Binance `BTCUSDT` 做了跨 `03:00` 边界的实测，观察最新 `5m` 桶 `03:00:00` 何时出现：

- `globalLongShortAccountRatio`：
  - `03:00:17 UTC` 已出现 `03:00:00`
- `topLongShortPositionRatio`：
  - `03:00:47 UTC` 已出现 `03:00:00`
- `openInterestHist`：
  - `03:01:25 UTC` 已出现 `03:00:00`
- `topLongShortAccountRatio`：
  - `03:02:06 UTC` 才出现 `03:00:00`

同时，`/fapi/v1/openInterest` 当前值接口接近实时；在 `2026-03-26 02:56:45 UTC` 的实测中，返回时间戳仅落后约 `4.3s`。

结论：

- `current OI` 可以按 `1m` 正常拉取
- `5m OI history / ratios` 不能在边界时刻单次请求
- 不能假设 4 个 endpoint 的最新桶发布时间一致
- 不能把不同 endpoint 的“各自最新桶”直接拼成一组数据；必须等同一个目标 `5m` 桶全部到齐后再写入

### 推荐抓取策略

对每个 `5m` 目标桶 `T`：

- 第一次尝试放在 `T + 20s`
- 若某 endpoint 返回的最新 `timestamp < T`，继续轮询
- 只有当以下 4 条数据都已经返回 `timestamp = T` 时，才认为该桶可提交：
  - `openInterestHist`
  - `globalLongShortAccountRatio`
  - `topLongShortAccountRatio`
  - `topLongShortPositionRatio`
- 在此之前，禁止把 `T` 和 `T-5m` 的数据混拼后写入 `md.open_interest_hist_5m / md.long_short_ratio_5m`
- 推荐尝试节奏：
  - `T + 20s`
  - `T + 45s`
  - `T + 75s`
  - `T + 105s`
  - `T + 135s`
  - 之后每 `30s` 一次
- 总等待上限：
  - `T + 5m`

这样做的好处是：

- 快接口不会被强行拖到 `+2m`
- 慢接口仍有机会在 `5m` 上限内补齐
- 调度逻辑比固定延迟一次性抓取更稳
- 能保证同一批 `5m` OI / ratio 原始数据在时间上严格对齐，避免后续窗口聚合出现假分歧

### 边界封片策略结论

本次明确采用：

- `方案 B：局部晚到，其他指标不等，只让 i25 / i26 自己晚到`

专项 runtime 修补设计见：[OI_ratio 晚到数据无阻塞修补方案 v1.0.0.md](/data/docs/OI_ratio%20晚到数据无阻塞修补方案%20v1.0.0.md)

含义：

- `OI / long_short_ratios` 的发布时间滞后，不应拖慢整包边界封片
- 现有其他指标继续按当前节奏推进
- 只有 `i25 open_interest` 和 `i26 long_short_ratios` 允许在边界后延迟写入
- 延迟原因只允许是“目标 `5m` 桶尚未在 4 个 REST endpoint 上全部到齐”

明确不采用：

- `方案 A：为了等 i25 / i26，对整个边界 snapshot 一起硬等待`

## 4. orderflow-market-data-ingestor 改造设计

## 4.1 新增 REST client 方法

在 `market_data_ingestor` 的 Binance REST client 中新增：

- `fetch_open_interest(symbol)`
- `fetch_open_interest_hist(symbol, period=5m, start_time, end_time, limit)`
- `fetch_global_long_short_account_ratio(symbol, period=5m, ...)`
- `fetch_top_long_short_account_ratio(symbol, period=5m, ...)`
- `fetch_top_long_short_position_ratio(symbol, period=5m, ...)`

实现位置建议：

- `/data/systems/market_data_ingestor/src/exchange/binance/rest/client.rs`
- 配套新增 REST DTO 文件：
  - `open_interest.rs`
  - `open_interest_hist.rs`
  - `long_short_ratio.rs`

## 4.2 新增标准化消息类型

### A. current OI

消息类型：

- `msg_type = "md.open_interest_current"`

推荐 routing key：

- `md.futures.open_interest.current.{symbol_lower}`

标准化字段：

```json
{
  "stream_name": "fapi/v1/openInterest",
  "ts_recv": "...",
  "ts_effective": "...",
  "open_interest_contracts": 10659.509,
  "mark_price": 71816.1,
  "open_interest_value_usdt": 765394630.0,
  "payload_json": {}
}
```

说明：

- `ts_effective` 取 Binance 返回时间
- `open_interest_value_usdt = open_interest_contracts * mark_price`
- `mark_price` 优先直接取当前 premium index / mark price；如果 REST 响应本身不带，则用最近一次 `md.mark_price` 或即时拉取后的值补齐

### B. OI 5m history

消息类型：

- `msg_type = "md.open_interest_hist_5m"`

推荐 routing key：

- `md.futures.open_interest.5m.{symbol_lower}`

标准化字段：

```json
{
  "stream_name": "futures/data/openInterestHist",
  "ts_recv": "...",
  "ts_effective": "...",
  "period": "5m",
  "open_interest_contracts": 20403.637,
  "open_interest_value_usdt": 150570784.0781,
  "payload_json": {}
}
```

说明：

- `ts_effective` 使用 Binance 历史记录时间戳
- 该表本身就是 `5m` 规范序列，不再做二次分钟化

### C. Long-Short Ratios 5m

消息类型：

- `msg_type = "md.long_short_ratio_5m"`

推荐 routing key：

- `md.futures.long_short_ratio.global_account.5m.{symbol_lower}`
- `md.futures.long_short_ratio.top_account.5m.{symbol_lower}`
- `md.futures.long_short_ratio.top_position.5m.{symbol_lower}`

标准化字段：

```json
{
  "stream_name": "futures/data/globalLongShortAccountRatio",
  "ts_recv": "...",
  "ts_effective": "...",
  "period": "5m",
  "ratio_type": "global_account",
  "long_short_ratio": 1.9559,
  "long_account_ratio": 0.6617,
  "short_account_ratio": 0.3382,
  "payload_json": {}
}
```

其中：

- `ratio_type ∈ {"global_account","top_account","top_position"}`

## 4.3 live 轮询任务

新增 2 类后台循环：

### current OI loop

- 频率：每 `1m`
- 只拉：
  - `/fapi/v1/openInterest`
- 写入：
  - DB
  - MQ / outbox

### 5m structure loop

- 频率：每 `5m` 闭合后
- 拉：
  - `/futures/data/openInterestHist?period=5m`
  - `/futures/data/globalLongShortAccountRatio?period=5m`
  - `/futures/data/topLongShortAccountRatio?period=5m`
  - `/futures/data/topLongShortPositionRatio?period=5m`
- 写入：
  - DB
  - MQ / outbox

实现约束：

- 这 4 条 `5m` REST 序列必须按“同一个目标桶 `T`”对齐采集
- 只有当 `openInterestHist + global_account + top_account + top_position` 都已经返回 `ts_bucket = T`，才允许把该桶写入本轮 live 输出
- 不允许为了“尽快出数”把 `T` 和 `T-5m` 混成一批写入
- 该等待逻辑应放在 `market_data_ingestor` 的 `5m structure loop` 内部处理，而不是让下游服务猜测某个 endpoint 是否已经补齐

## 4.4 startup backfill

新增一组 backfill 任务，风格与当前 funding / premium bootstrap 一致：

- 启动时补齐最近 30 天：
  - OI 5m 历史
  - Global ratio 5m 历史
  - Top account ratio 5m 历史
  - Top position ratio 5m 历史

### backfill 原则

- 只补 `5m` 规范序列
- 不补 `15m / 4h / 1d / 3d`
  - 这些窗口全部由 indicator_engine 聚合

- `open_interest_contracts double precision not null`
- `open_interest_value_usdt double precision not null`

建议唯一键：

- `(market, symbol, ts_bucket)`

- `ratio_type text not null`
- `long_short_ratio double precision not null`
- `long_account_ratio double precision`
- `short_account_ratio double precision`

建议索引：

### 备注

这里坚持把三种 ratio 放一张表，而不是拆三张表，原因是：

## 6. orderflow-indicator-engine 改造设计

## 6.1 配置层改造

当前 `indicator.window_codes` 只接受：

- `1m`
- `15m`
- `1h`
- `4h`
- `1d`
- `3d`

代码和配置都还不接受 `5m`。[bootstrap.rs](/data/systems/indicator_engine/src/app/bootstrap.rs#L658) [bootstrap.rs](/data/systems/indicator_engine/src/app/bootstrap.rs#L1591) [config.yaml](/data/config/config.yaml#L63)

因此必须先做这一步：

- 在 `default_window_codes()` 中加入 `5m`
- 在配置校验中加入 `5m`
- 在 `config.yaml` 中把 `indicator.window_codes` 扩为：
  - `["1m", "5m", "15m", "1h", "4h", "1d", "3d"]`

说明：

- 这里的 `5m` 是为了让新指标 `i25 / i26` 能合法出现在统一窗口体系中
- 不是要求所有旧指标都必须补做 `5m`
- 旧指标若不支持 `5m`，可以继续维持现状；本次只要求 `i25 / i26` 的 `by_window` 必须覆盖 `5m / 15m / 4h / 1d / 3d`

## 6.2 ingest / replay 改造

indicator_engine 现在的 replay SQL 只 union：

- `md.agg.trade.1m`
- `md.agg.orderbook.1m`
- `md.agg.liq.1m`
- `md.agg.funding_mark.1m`

本次需要追加 3 类输入：

- `md.open_interest_current`
- `md.open_interest_hist_5m`
- `md.long_short_ratio_5m`

改造点：

- live MQ 消费：
  - 新增解码这 3 类 `msg_type`
- startup replay / canonical replay：
  - 从新建的 `md.*` 表把这 3 类数据 union 进事件流

### 设计原则

- `open_interest_hist_5m` 和 `long_short_ratio_5m` 是**窗口计算主输入**
- `open_interest_current` 只是 current sidecar，不参与 `15m/4h/1d/3d` 主窗口计算
- `indicator_engine` 不应在 `5m / 15m / 4h / 1d / 3d` 边界按 wall-clock 盲等固定秒数
- `indicator_engine` 只应根据“最新完整可用的公共 `5m` 桶”推进 `i25 / i26` 的窗口计算与封片
- 本次采用“局部晚到”策略：
  - 其他现有指标不因 `i25 / i26` 缺桶而等待
  - 只有 `i25 / i26` 本身允许晚到

## 6.3 runtime state 改造

在 runtime state 中新增 3 组缓冲：

### A. current OI slot

保存最近一个 current OI：

- `ts_effective`
- `open_interest_contracts`
- `mark_price`
- `open_interest_value_usdt`

### B. OI 5m deque

按时间排序保存最近足够覆盖 `3d` 的 5m 点：

- `ts_bucket`
- `open_interest_contracts`
- `open_interest_value_usdt`
- `reference_price`

最少保留：

- `864 + 安全余量`

### C. long-short ratio 5m deque

分别为三种 ratio_type 维护 5m 序列：

- `global_account`
- `top_account`
- `top_position`

每个点保存：

- `ts_bucket`
- `long_short_ratio`
- `long_account_ratio`
- `short_account_ratio`

### D. latest common complete bucket

在构造 `WindowBundle` / `IndicatorContext` 时按当前已缓存序列现算：

- `latest_complete_oi_bucket`
- `latest_complete_ratio_bucket_global`
- `latest_complete_ratio_bucket_top_account`
- `latest_complete_ratio_bucket_top_position`
- `latest_common_oi_ratio_bucket = min(以上 4 个 bucket)`

约束：

- `i25 / i26` 只允许基于 `latest_common_oi_ratio_bucket` 及其之前的 `5m` 序列做窗口聚合
- 当 `5m / 15m / 4h / 1d / 3d` 边界刚到，但 `latest_common_oi_ratio_bucket` 还没推进到该边界时：
  - 不阻塞整个 `indicator_engine`
  - 只是不把 `i25 / i26` 对应边界的窗口视为 ready
  - 其他现有指标继续按原节奏封片，不被 `i25 / i26` 拖慢
- 一旦 `latest_common_oi_ratio_bucket` 推进到目标边界，再补发该边界对应的 `feat.*` 和 `temp_indicator` 切片

## 7. 指标口径设计

## 7.1 i25 open_interest

## 目标

为上层提供：

- 当前 OI 是否在上升/下降
- 价格与 OI 的组合关系
- 当前 move 更像：
  - `leveraged_long_build`
  - `fresh_short_build`
  - `long_unwind`
  - `short_cover`

## 规范输入

主输入一律使用 `5m` OI history：

- `OI_t = open_interest_value_usdt`
- `P_t = 同时刻参考价格`

参考价格优先级：

1. 同时刻 `mark_price`
2. 若缺失，则最近 futures mark price
3. 再缺失则使用 futures 价格 close

## 计算窗口

所有窗口都从 `5m` 序列聚合：

- `5m = 1`
- `15m = 3`
- `4h = 48`
- `1d = 288`
- `3d = 864`

## 核心字段

每个窗口至少输出：

- `window_minutes`
- `samples_used`
- `oi_start`
- `oi_end`
- `oi_delta_abs`
- `oi_delta_pct`
- `oi_log_return`
- `oi_zscore`
- `oi_accel`
- `price_start`
- `price_end`
- `price_delta_pct`
- `price_oi_relation`
- `state`

## 分类口径

### leveraged_long_build

- 价格涨
- OI 涨

### fresh_short_build

- 价格跌
- OI 涨

### long_unwind

- 价格跌
- OI 跌

### short_cover

- 价格涨
- OI 跌

### neutral

- 其余情况

## 7.2 i26 long_short_ratios

## 目标

为上层提供：

- 全市场是否拥挤多 / 拥挤空
- Top Trader 是否比全市场更偏一侧
- 账户比与持仓比是否同步变极端

## 规范输入

使用三条 `5m` 序列：

- `global_account`
- `top_account`
- `top_position`

## 核心字段

每个窗口至少输出：

- `global_ratio_latest`
- `top_account_ratio_latest`
- `top_position_ratio_latest`
- `global_ratio_log`
- `top_account_ratio_log`
- `top_position_ratio_log`
- `global_ratio_change`
- `top_account_ratio_change`
- `top_position_ratio_change`
- `account_crowding_gap`
- `position_crowding_gap`
- `crowding_stretch`
- `crowding_zscore`
- `crowding_state`

## crowding_state 口径

仅允许：

- `crowded_long`
- `crowded_short`
- `long_crowding_unwind`
- `short_crowding_unwind`
- `balanced`

推荐联调顺序：

1. 先只做 ingestor，把 `md.*` 表和 MQ 路由打通
2. 再做 indicator_engine 的 ingest / replay
3. 再做 `i25 / i26`
4. 最后检查 `temp_indicator` 的最终 JSON 契约

这样可以把问题快速切分为：

- 是源没进来
- 还是 DB 没落
- 还是 replay 没吃到
- 还是指标没算出来
- 还是 snapshot/temp_indicator 没映射出来

## 15. SQL 草案骨架

## 15.1 设计原则

- 新增 `md.*` 表建议保持为普通表，理由和现有 `md.agg_*` 一致：
  - 写入量低
  - 需要稳定 natural upsert key
  - 不值得为低频 REST 数据引入 hypertable 唯一键限制
- 新增 `feat.*` 表继续使用 hypertable，和现有 `feat.trade_flow_feature / feat.funding_feature` 风格保持一致。
- 所有新表都沿用：
  - `venue`
  - `market`
  - `symbol`
  - `source_kind`
  - `payload_json / extra_json`
- 对 `_5m` 规范表，不再重复存 `period_code='5m'` 这类冗余列，避免增大行宽和唯一索引宽度。
- 除幂等唯一键外，只保留与真实查询路径匹配的一条次级 lookup 索引，不预先堆叠多条“可能会用到”的索引。
- 新增 `feat.*` 表不加 GIN，也不做激进 autovacuum override；这两张表写入量远低于 `feat.indicator_snapshot`，先沿用默认 autovacuum，后续只在真实观测到 vacuum lag 时再调优。

## 16. 结论

这次改造的本质不是“再加两个指标”，而是给当前系统补上**仓位结构数据源**。

真正需要落地的是三件事：

- `market_data_ingestor` 把 Binance 的 `OI` 和 `Long-Short Ratios` 拉进来，并写入 `md.*`
- 数据库新增 `md.*` 和 `feat.*` 表，保证可回放、可诊断、可重算
- `indicator_engine` 把这批 `5m` 规范序列聚合成 `5m / 15m / 4h / 1d / 3d`，并写入 `temp_indicator`

只要这三层按本文设计打通，上层以后怎么用这些字段，是下一阶段的事；本次任务到此为止。
