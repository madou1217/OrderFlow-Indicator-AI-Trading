# 指标 v3：Binance Options 最小可落地接入方案

> 本文只讨论以下范围：
> - `orderflow-market-data-ingestor`
> - 数据库改造
> - `orderflow-indicator-engine`
> - 最终写入 `/data/systems/llm/temp_indicator/*.json` 的指标结构
>
> 本文**不讨论**：
> - LLM prompt
> - `stage1 scan / stage2 entry` 如何消费期权指标
> - 复杂期权定价模型与交易策略

---

## 1. 目标与边界

本次新增一层**期权状态信息**，服务于 `4H-1D` 的标的交易，而不是做一个完整的期权交易系统。

目标补齐四类最有交易价值的信息：

- `ATM IV`
- `RR / skew`
- `gamma exposure proxy`
- `major expiry strikes`

目标不是把完整期权链都原样送到上层，而是给上层补一层：

- 当前隐含波动率处于什么水平
- 偏度是否明显偏向 put / call
- gamma 约束是偏 pin、偏加速，还是中性
- 近期主要到期日的 call wall / put wall 在哪

本次设计的硬边界：

- 只做 `BTC` / `ETH` 对应的 options sidecar
- 只接 Binance Options 公共市场数据
- 不改变现有 `spot/futures` 主链指标的计算逻辑
- 不把期权链强行塞进现有 `cfg.market_type = ('spot','futures')`
- 不把完整 options 微结构做成新的 1m 决策层

---

## 2. 先说结论：需要新数据源，但不需要重做整套架构

这四类期权信息都**不能从现有现货/永续数据推导出来**，所以必须接新的 Binance Options 数据源。

但不需要把当前架构推翻重来。

推荐做法不是：

- 把 `options` 变成第三种 `market_type`
- 然后让所有现有 `md.* / feat.* / runtime` 都理解 spot / futures / options 三种市场

推荐做法是：

- 把 options 接成一条**独立的 sidecar 数据链**
- 在 `indicator_engine` 里新增 2 个 options 指标
- 让它们像 `i25/i26` 一样，服务于高时间框架状态层

这条路线的改动量是**中等**，不是小修小补，但也不是架构级重写。

---

## 3. Binance Options 能直接给什么，哪些需要自己聚合

### 3.1 官方可直接获取的基础数据

Binance Options 公共 API 足够支撑这套最小方案：

- `GET /eapi/v1/exchangeInfo`
  - 合约列表
  - `symbol`
  - `underlying`
  - `strikePrice`
  - `expiryDate`
  - `side` (`CALL/PUT`)
  - `unit`
- `GET /eapi/v1/index`
  - 标的指数价
- `GET /eapi/v1/mark`
  - `markPrice`
  - `bidIV`
  - `askIV`
  - `markIV`
  - `delta`
  - `gamma`
  - `vega`
  - `theta`
- `GET /eapi/v1/openInterest`
  - 指定 `underlyingAsset + expiration` 下各期权合约的
  - `sumOpenInterest`
  - `sumOpenInterestUsd`

这意味着：

- `ATM IV`：可以自己算
- `RR / skew`：可以自己算
- `major expiry strikes`：可以自己聚合
- `gamma exposure`：可以算 **proxy**

### 3.2 需要明确的限制

Binance 不会直接给你：

- `25d RR`
- `25d butterfly`
- `net dealer gamma exposure`
- `max pain`
- `gamma flip level`

这些都需要自己从链级数据聚合。

尤其要明确：

- 用公开 API 只能做 **gamma exposure proxy**
- 不能声称自己拿到了真实的 dealer net GEX

因为你有：

- 每个合约的 `gamma`
- 每个合约的 `open interest`

但你没有：

- 市场参与者净方向
- dealer inventory sign

所以最诚实的命名应当是：

- `gamma_exposure_proxy`
- 或 `listed_gamma_concentration`

## 4. 推荐的最小落地架构

## 4.1 不改现有 `market_type`

当前系统里：

- `market_data_ingestor` 的 `Market` 只有 `spot/futures`
- 数据库 `cfg.market_type` 也只有 `spot/futures`

这次不建议把它扩成 `spot/futures/options`。

原因：

- 现有 26 个指标的主链假设就是 spot/futures 双市场
- options 不是新的 1m canonical price stream
- options 更像高时间框架状态 sidecar

所以本次采用：

- **独立的 options REST 拉取**
- **独立的 options md 表**
- **独立的 options feat 表**
- 在 `indicator_engine` 中以 sidecar 方式聚合

## 4.2 推荐最终新增 2 个指标，而不是 1 个大杂烩指标

推荐新增：

- `i27 options_surface`
- `i28 options_positioning`

不推荐做成 1 个 `options_regime` 大指标。

原因：

- `ATM IV / RR / skew` 是一类问题：隐波曲面与偏度
- `gamma / expiry strikes` 是另一类问题：仓位分布与到期约束
- 两者计算来源不同、字段密度不同、晚到策略也可能不同
- 拆成 2 个指标后，上层更容易读，也更容易单独修复

如果只想最小上线顺序：

1. 先做 `i27 options_surface`
2. 再做 `i28 options_positioning`

但目标架构应直接按 2 个指标设计。

## 5. `orderflow-market-data-ingestor` 需要新增什么

## 5.1 新增 Binance Options REST client

新增一组 options REST client 方法：

- `fetch_options_exchange_info()`
- `fetch_options_index_price(underlying)`
- `fetch_options_mark(symbol)`
- `fetch_options_open_interest(underlying_asset, expiration)`

建议新增目录：

- `/data/systems/market_data_ingestor/src/exchange/binance/rest/options_exchange_info.rs`
- `/data/systems/market_data_ingestor/src/exchange/binance/rest/options_index.rs`
- `/data/systems/market_data_ingestor/src/exchange/binance/rest/options_mark.rs`
- `/data/systems/market_data_ingestor/src/exchange/binance/rest/options_open_interest.rs`

说明：

- `exchangeInfo` 不需要高频拉取
- `mark` 和 `openInterest` 才是核心时序数据

## 5.2 采样节奏

推荐节奏：

- `exchangeInfo`：
  - 启动时拉一次
  - 之后每 `1h` 刷新一次
- `index`：
  - 每个 `5m` bucket 拉一次
- `mark`：
  - 每个 `5m` bucket 拉全链一次
- `openInterest`：
  - 每个 `5m` bucket，按 expiry 逐个拉一次

本次不建议做 options websocket。

理由：

- 目标是 `4H-1D` 状态层，不是秒级触发层
- `5m` 规范桶已经足够
- REST 更容易先稳定落地

## 5.3 链级扫描方式

对每个 `underlying`：

- `BTCUSDT`
- `ETHUSDT`

在每个 `5m` 目标桶 `T`：

1. 用 `exchangeInfo` 得到当前 live symbol 列表
2. 过滤出属于该 `underlying` 的 live contracts
3. 用 `index` 取标的价格
4. 对 live contracts 拉 `mark`
5. 对每个 live expiry 拉 `openInterest`
6. 写入链级 md 表

这里的关键不是省请求，而是：

- 同一 `5m` 桶要构成一张**一致的 options chain snapshot**

## 6. 建议新增哪些 `md.*` 表

本次推荐只新增 2 张时序表，不新增 catalog 表。

原因：

- `exchangeInfo` 的字段可直接冗余到 md 行里
- 这样最小化表数量
- 不引入额外 join

## 6.1 `md.option_mark_greeks_5m`

用途：

- 存每个期权合约在 `5m` 桶上的 mark + IV + Greeks snapshot

建议字段：

- `ts_bucket`
- `venue`
- `underlying`
- `symbol`
- `expiry_ts`
- `strike_price`
- `contract_side` (`CALL/PUT`)
- `unit`
- `index_price`
- `mark_price`
- `bid_iv`
- `ask_iv`
- `mark_iv`
- `delta`
- `gamma`
- `vega`
- `theta`
- `risk_free_interest`
- `payload_json`

主键建议：

- `(venue, symbol, ts_bucket)`

## 6.2 `md.option_open_interest_5m`

用途：

- 存每个期权合约在 `5m` 桶上的 open interest snapshot

建议字段：

- `ts_bucket`
- `venue`
- `underlying`
- `symbol`
- `expiry_ts`
- `strike_price`
- `contract_side`
- `unit`
- `sum_open_interest`
- `sum_open_interest_usd`
- `payload_json`

主键建议：

- `(venue, symbol, ts_bucket)`

## 6.3 为什么不直接只存聚合结果

如果只存最终聚合结果，例如只存：

- ATM IV
- RR25
- call wall / put wall

短期能跑，但后面会有两个问题：

- 无法回放和重算聚合逻辑
- 一旦你改 RR / GEX 算法，就没有底层链级数据可重建

所以最小可落地方案里，`md` 仍然应该存**链级 snapshot**。

## 8. 两个新指标具体做什么

## 8.1 `i27 options_surface`

职责：

- 只解释隐波与偏度，不解释仓位墙

最小输出建议：

- `atm_iv`
- `atm_iv_regime`
- `rr_25d`
- `skew_state`
- `term_structure_state`

### 计算建议

#### ATM IV

对某个 expiry：

1. 取当前 `index_price`
2. 找最接近 ATM 的 strike
3. 取该 strike 的 call / put `markIV`
4. ATM IV 取：
   - `call_mark_iv` 与 `put_mark_iv` 的均值
   - 若一侧缺失则降级取另一侧

#### RR / skew

推荐：

- 用 delta 最接近 `+0.25` 的 call 和 `-0.25` 的 put
- `rr_25d = iv_call_25d - iv_put_25d`

若没有精确 25d：

- 用最近 delta bucket 近似
- 第一版不做复杂插值也可以

`skew_state` 可离散成：

- `put_skewed`
- `call_skewed`
- `neutral`
- `unclear`

#### term structure

可比较：

- front expiry ATM IV
- second expiry ATM IV

离散成：

- `front_rich`
- `back_rich`
- `flat`
- `unclear`

## 8.2 `i28 options_positioning`

职责：

- 只解释 expiry 约束与 gamma 墙，不解释 IV 曲面

最小输出建议：

- `gamma_exposure_proxy`
- `gamma_state`
- `call_wall_strike`
- `put_wall_strike`
- `expiry_pressure_state`

### 计算建议

#### gamma_exposure_proxy

对每个合约：

- `gamma_exposure_proxy_contract`
  = `gamma * open_interest * unit * index_price`

然后按：

- 全 expiry 聚合
- 或重点 expiry 聚合

注意：

- 这是 **proxy**
- 不是 dealer true net GEX

#### major expiry strikes

对每个 expiry：

- 按 strike 聚合 call OI
- 按 strike 聚合 put OI
- 找最大 OI 的几个 strike

可以输出：

- `call_wall_strike`
- `put_wall_strike`
- `top_call_oi_strikes_json`
- `top_put_oi_strikes_json`

#### gamma flip level proxy

第一版不要做复杂 root finding。

可以先做一个更实用的 proxy：

- 找 gamma concentration 最强的上下两个 strike cluster
- 用它们夹出的区域作为 gamma flip proxy zone

## 9. 为什么推荐 2 个指标，而不是 1 个

如果做成 1 个大指标：

- `atm_iv`
- `rr`
- `skew`
- `gex`
- `expiry strikes`

全塞在一起，会有 3 个问题：

1. 语义太杂
2. 一旦某条链缺数据，整个 options 指标都变脏
3. 后面很难做 late patch / repair

拆成 2 个后：

- `surface` 缺失，不影响 `positioning`
- `positioning` 晚到，不必拖住 `surface`
- 上层也更容易理解：
  - 一个是 volatility regime
  - 一个是 positioning regime

## 10. 与当前系统的衔接方式

## 10.1 在 `temp_indicator` 中的建议结构

推荐最终写成：

```json
{
  "indicators": {
    "options_surface": {
      "5m": {},
      "15m": {},
      "4h": {},
      "1d": {},
      "3d": {}
    },
    "options_positioning": {
      "5m": {},
      "15m": {},
      "4h": {},
      "1d": {},
      "3d": {}
    }
  }
}
```

## 10.2 它在交易流程里的定位

这两个指标不属于：

- 触发层
- 1m execution 层

它们属于：

- 状态层
- 约束层

它们回答的是：

- 当前隐波环境是压缩、抬升还是偏斜
- 当前 expiry / gamma 墙对路径有没有 pin 或 acceleration 影响

所以它们更接近：

- `funding`
- `VPIN`
- `OI`
- `long_short_ratios`

而不是：

- `footprint`
- `orderbook_depth`
- `absorption`

## 11. 最小上线顺序

推荐顺序：

### 第一步

先打通链级 md 表：

- `md.option_mark_greeks_5m`
- `md.option_open_interest_5m`

### 第二步

先上线：

- `i27 options_surface`

原因：

- 计算最直接
- `ATM IV / RR / skew` 的解释稳定
- 不会碰到“GEX 到底是不是净 dealer gamma”这种语义争议

### 第三步

再上线：

- `i28 options_positioning`

原因：

- `gamma_exposure_proxy` 和 `major expiry strikes` 对交易有价值
- 但定义边界比 IV/skew 更容易引起误用

---

## 12. 最终建议

从“最小可落地”的角度，我推荐：

- 不引入完整 options websocket
- 不扩展现有 `market_type`
- 只新增 2 张链级 `md` 表
- 只新增 2 张聚合 `feat` 表
- 只新增 2 个 indicator

也就是：

- `i27 options_surface`
- `i28 options_positioning`

这是当前系统最合理的接法。

它满足：

- 数据源真实可拿
- 工程改动可控
- 与现有 `i25/i26` 风格一致
- 对 `4H-1D` 的交易决策有明确增益

如果只允许做最小上线版本：

- **先做 `i27 options_surface`**
- `i28 options_positioning` 紧随其后

这比试图一次做完整 options market stack 更稳，也更符合当前系统的目标。
